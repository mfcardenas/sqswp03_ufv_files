# Game Database Structure

## Overview

All games share a common core schema. Each attempt is tagged by a `game_key` enum value.

In most cases, adding a new game does **not** require a new core table. You add a new `game_key` and store game-specific detail in `metadata` (or add a game-specific detail table if needed).

---

## Tables

### 1. `game_profiles`

Each user has **one** game profile, shared across all games.

| Column     | Type      | Description                          |
|------------|-----------|--------------------------------------|
| id         | TEXT (PK) | Unique profile ID                    |
| user_id    | TEXT (FK) | References `users.id`                |
| nickname   | TEXT      | Display name for leaderboards        |
| university | TEXT      | Player university                    |
| created_at | TIMESTAMP | Record creation time                 |
| updated_at | TIMESTAMP | Last update time                     |

Rules:
- `user_id` is unique (one profile per user).
- `nickname` is unique at DB level.
- Application also enforces case-insensitive nickname uniqueness.

---

### 2. `game_attempts`

Every play session of any game creates one attempt row.

| Column              | Type              | Description                                      |
|---------------------|-------------------|--------------------------------------------------|
| id                  | TEXT (PK)         | Unique attempt ID                                |
| user_id             | TEXT (FK)         | References `users.id`                            |
| game_key            | GameKey (ENUM)    | Which game was played                            |
| status              | GameAttemptStatus | `STARTED`, `COMPLETED`, `ABANDONED`             |
| started_at          | TIMESTAMP         | Attempt start time                               |
| completed_at        | TIMESTAMP         | Attempt finish time (nullable)                   |
| duration_ms         | INTEGER           | Duration in milliseconds                         |
| score               | INTEGER           | Final score                                      |
| max_score           | INTEGER           | Maximum possible score                           |
| correct_count       | INTEGER           | Correct answers/actions                          |
| incorrect_count     | INTEGER           | Incorrect answers/actions                        |
| nickname_snapshot   | TEXT              | Nickname at play time                            |
| university_snapshot | TEXT              | University at play time                          |
| metadata            | JSONB             | Game-specific detail                             |
| created_at          | TIMESTAMP         | Record creation time                             |
| updated_at          | TIMESTAMP         | Last update time                                 |

## Enums

### `GameKey`
Current values in this project:
- `QUIZ_12207`
- `ROLLERCOASTER_29110`

### `GameAttemptStatus`
- `STARTED`
- `COMPLETED`
- `ABANDONED`

---

## Why Snapshots Exist

`nickname_snapshot` and `university_snapshot` preserve leaderboard history as it was at play time, even if profile values change later.

---

## Metadata (JSONB)

`metadata` is flexible and game-defined.
Use core columns (`score`, `correct_count`, `duration_ms`) for aggregates; use `metadata` for detailed per-game payloads.

Example:
```json
{
  "choices": ["option_a", "option_b"],
  "path_taken": "safety_first"
}
```

---

## Leaderboard Logic

Leaderboard is generated by:
1. `status = 'COMPLETED'` and `completed_at IS NOT NULL`
2. Filter by `game_key`
3. Sort by:
   - `score` DESC
   - `duration_ms` ASC
   - `completed_at` ASC
   - `created_at` ASC
4. Keep only the best attempt per user

---

## How to Integrate a New Game

1. Add new `GameKey` enum value (DB migration).
2. Add same key in app constants and validation layer.
3. On game start, create `game_attempts` row with `status='STARTED'`.
4. On game completion, update same row with totals + `metadata`, set `status='COMPLETED'`.
5. Leaderboard/profile integration works on this shared model.

---

## Important Note

For many games, core tables are enough.
If a game needs structured per-round/per-level analytics, create an additional game-specific detail table linked to `game_attempts.id`.
